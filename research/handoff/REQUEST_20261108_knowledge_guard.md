# REQUEST — 지식 층이 "저절로 쌓이게" 하는 장치 검토 (2026-11-08 저녁)

답은 `research/handoff/REPLY_20261108_knowledge_guard.md` 한 파일로. 다른 파일은 만들거나 고치지 말 것(코드·docs·DB·배치 실행 금지, hook 실행 금지).

## 배경 (실측)
오늘 지식 세 층(규칙 CLAUDE.md / 지식 KNOWLEDGE·DECISIONS·PITFALLS / 기록)을 만들었고 Codex 1차 검토(`REPLY_20261108_knowledge_layers.md`)를 반영했다(`CHECK_20261108_knowledge_layers.md`). 남은 문제는 **사람(또는 기억 없는 Claude)이 두 가지를 빠뜨리는 것**: ① 세션마다 세 장에 한 줄 적기 ② 월 1회 압축·정정. 사용자 요구: "지침으로 자동이 되게, 자동으로 쌓이는 걸 감안한 구조로, 복잡하거나 오래 걸리는 부작용 없이."
그래서 Claude Code hook 두 개를 달았다(`.claude/settings.json` → `tests/knowledge_guard.py`, patch_note `20261108_knowledge_guard.md`):
- SessionStart: 세 장 검사 + 마지막 정리 뒤 며칠·worklog 몇 건·세 장이 안 가리키는 새 연구/판정 파일 목록 → 30일 또는 10건이면 "정리 제안" 지시.
- Stop: 기록 층만 바뀌고 세 장이 그대로면 끝내기를 한 번 막음. 빠져나가는 길 = worklog 에 `지식 층: 변경 없음(이유)`.
- 실측 0.3초, git 작업본만, 예외는 통과, 같은 상태 두 번 안 막음.

## 부탁 (5개, 실측/제안 구분 · 각 제안에 기대 이득 한 줄 + 비용 한 줄)
1. **빠져나갈 구멍**: 이 장치를 통과하면서도 지식이 안 쌓이는 경로를 구체적으로(예: 세 장을 한 글자만 고침 · `변경 없음` 선언 남용 · 커밋 뒤 작업본이 깨끗해져 감시가 못 봄 · 보조 세션/worktree 에서 작업). 각 구멍에 **가장 싼 막는 법** 하나씩(막을 가치가 없으면 "두어도 됨"이라고).
2. **"정리할 거리" 계산이 맞나**: `tidy_backlog()`(파일명 날짜 > 마지막 정리 날짜이고 파일 stem 이 KNOWLEDGE/DECISIONS 본문에 없음)이 놓치는 것·잘못 잡는 것. worklog 안의 "사용자 결정" 절과 DECISIONS 행을 잇는 더 나은 방법이 있으면(1차 답의 `check_knowledge_drift` 제안을 여기 합칠 수 있나).
3. **정리 세션 자체를 반자동으로**: 월 1회 정리를 "사람이 기억"이 아니라 장치가 시작하게 하는 가장 단순한 길(SessionStart 문맥의 지시로 충분한가, 아니면 별도 명령/스킬/스케줄이 나은가). 복잡해지는 쪽은 반대 근거와 함께.
4. **부작용**: 이 hook 이 일으킬 수 있는 귀찮음·느려짐·오탐(예: 문서만 고치는 짧은 세션, 배치 시간대, Codex 가 쓴 REPLY 파일이 기록 층으로 잡힘 — 지금은 `handoff/CHECK_*` 만 포함, REPLY/REQUEST 제외). 완화책과 함께. "끄는 법"이 사용자에게 쉬운지도.
5. **구조가 커질 때**: 세 장이 상한(24KB·15KB·5KB)에 닿으면 어떻게 나누는 게 맞나(자리별 파일? 닫힌 결론 보관소?). 지금 결정하지 말고 **닿았을 때의 규칙**만 한 줄로.

제안은 "지금 당장 넣을 것(≤30줄)"과 "나중"으로 나눠 달라. 규칙 완화(판정·0-diff·배치 시간)는 제안이 아니다.
