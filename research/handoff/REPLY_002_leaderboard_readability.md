### 특히 오해가 큰 실제 데이터 연결

- **sv_a**: 현재 h20 IC +0.0330, n=20, 95% CI [+0.0145, +0.0508]. 별도 지표인 exc20은 +0.52%p, n=20, 95% CI [−0.01, +1.14]다. `conf()`는 IC CI만 보고 ‘●●● 우연 아님’을 반환하고, `translate()`는 이를 초과수익 문장 뒤에 붙인다. **초과수익 CI가 0을 걸치는데도 초과수익이 우연과 구분된다고 읽힐 수 있다.** 확정 판정은 registry의 ‘기움·채택 아님’이다.
- **‘이긴 비율’**: `h20.pos`는 앵커 IC가 양수인 비율이다. 시장 대비 초과수익이 양수인 비율이나 매매 승률이 아니다. `translate()`의 ‘20일 뒤 시장보다 …, …번 이김’은 두 지표를 하나의 성공률처럼 연결한다(216~218, 260행).
- **상단과 상세의 다른 라벨**: v30은 확정 ‘유의’와 자동 ‘기움’, lv_b는 확정 ‘기움’과 자동 ‘노이즈’가 함께 존재한다. 이 차이는 잘못된 판정이라고 결론 낼 근거가 아니다. **판정 시점·표본이 다른 값임을 붙이지 않은 표현**이 문제다. 제목 ‘현재 계산 / 확정 판정(날짜)’으로 구분해야 한다.
- **‘최근’의 기준도 다름**: cross_sim.trailing.asof는 20260910, alpha_beta.asof는 20260911이다. recent_ic는 생성일과 앵커 기간을 따로 갖는다. ‘어제’를 ‘마지막 관측일’로 바꾸고 각 패널의 기존 날짜를 가까이 표시해야 한다. 데이터 날짜와 JSON 생성일을 혼용하지 않는다.

### 390px에서의 모습 — CSS 기반 추정

실측 CSS: wrap 좌우 padding 각 16px, card padding 각 12px, table은 `white-space:nowrap`, active 마지막 열은 `min-width:300px`다. 800px 이하에서 바뀌는 것은 howto의 3열→1열, 진행 막대 너비뿐이다.

**추정**: 390px 화면에서는 표 내용 폭이 약 330px 남아 8·9열을 동시에 볼 수 없다. 오른쪽의 확정 상태·문장까지 읽으려면 가로 스크롤이 필요하고, 모델명은 가로 방향으로 고정되어 있지 않아 맥락을 놓칠 수 있다. howto 설명 3개가 세로로 쌓여 실제 성적을 더 아래로 밀어낸다. 첫 화면의 정확한 접힘 위치는 기기·폰트·화면 높이를 실측해야 한다.

`title` 툴팁만 있는 n·CI·문서명은 터치에서 접근이 확실하지 않다. 특히 원본 표의 초과수익 n·CI는 title에 있고, 활성 표의 IC CI는 보이지 않는다. 보조 문구가 11~12.5px라 작은 화면에서 읽기 부담이 있을 것으로 추정한다. 색 대비 통과 여부는 이번에 측정하지 않았다.

원래 판정 이름은 배지에 유지하고 설명을 붙인다. 용어만 바꾸어 새로운 판정 단계를 만들지 않는다.

‘IC 0.01 ≈ 시장초과 …’, ‘+0.05면 프로가 돈 버는 수준’ 같은 수익 환산·절대 수준 설명은 삭제한다. 현재 데이터로 일반적인 수익 환산이나 모든 트랙 공통 기준을 제공할 수 없고, 이번에는 새 환산 지표를 만들지 않는다.

## 3. 구조·디자인 제안 — 효과 큰 순

### P0-1. 첫 화면은 ‘역할 → 현재 확인 가능한 성적 → 다음 검토’ 3개

1. **내 운용 기준**: `registry.live`의 lv_b를 첫 카드에 고정. ‘사용자가 정한 운용 기준’과 ‘확정: 기움·채택 아님’을 동시에 보여 준다. `reference`의 v30은 다음 줄에 참고 챔피언으로 둔다. 다른 모델에 ‘따라 보기’ 버튼을 만들지 않는다.
2. **성적과 근거**: money 대상의 수치를 모델별로 분리하여 보여 준다. 기간·비교 대상·n·CI가 한 묶음이다. 최근 성적의 CI가 없는 지금은 아래 ‘데이터 제약’ 정책을 따른다. 누적 검증 수치를 최근 수익으로 바꿔 부르지 않는다.
3. **다음 검토**: 최소 관측기간 진행과 확정된 재판정 계획을 구분한다. ‘결과에 따라 유지 또는 재검토, 자동 교체 없음’을 함께 표시한다. 현재 JSON만으로 알 수 없는 일정은 ‘일정 정보 미제공’으로 남긴다.

왜: 사용자가 자신이 보는 모델의 역할과 현재 결정 상태를 먼저 이해하고 숫자를 해석할 수 있다. 긴 읽는 법 3개는 이 아래 접힌 설명으로 옮긴다. 3개 카드가 첫 화면 안에 들어가는지는 실제 390px 렌더 후 확인한다.

### P0-2. 성적순 정렬을 역할별 고정 순서로 교체

- 상단 성적 대상은 `registry.money`로 제한하고 live→reference 순서를 적용한다. 현재 money=[v30,lv_b]이므로 배열의 순서 그대로가 아니라 역할을 반영한다.
- 나머지는 ‘관측 중인 모델’로 접고 트랙별로 분리한다. 판정 전·판정 완료·은퇴는 텍스트 상태로 구분한다. 은퇴 모델의 과거 기록은 유지한다.
- active의 exc20 내림차순(254~256행)과 원본의 전체 트랙 IC 내림차순(269~272행)을 없앤다. 특히 large는 별도 구역에 두고 ‘설계 평가기간 60~120거래일, h20은 보조’라고 표시한다.

왜: 위에 있는 모델을 더 좋은 운용 대안으로 읽는 경향을 줄인다. 트랙 구분선만 둔 전체 IC 순위표는 피한다.

### P0-3. 확정 판정과 현재 통계는 같은 배지를 공유하지 않기

- 카드 상단: registry.sealed의 확정 판정과 날짜.
- 바로 아래: ‘현재 누적 계산’의 IC·n·CI. 자동 verdict는 펼친 상세에 ‘자동 참고’라고 표시한다.
- 정본의 doc는 실제 열 수 있는 경로를 확인한 뒤 ‘판정 근거 읽기’ 링크로 제공한다. 현재 title의 파일명만으로는 문서를 열 수 없다.
- registry 로드 실패 시 ‘판정 기록을 불러오지 못함’을 표시한다. 낡은 인라인 값을 최신 확정 상태처럼 제시하지 않는다. live/reference를 확정할 수 없으면 행동 링크를 보류한다.

왜: 표본이 늘어 자동 값이 달라져도 과거 결정을 지우거나 새 결정을 내린 것처럼 보이지 않는다.

### P1-1. 모바일에서는 표 한 행을 모델별 카드로

- 600px 이하 제안: 모델명·역할·확정 배지, 지표명/값, ‘채점 완료 n일 · 95% CI [하단, 상단]’, 상세 열기 순서. 설명은 줄바꿈을 허용한다.
- IC·초과수익을 동시에 넣더라도 각자의 n·CI를 바로 아래 붙인다. 화면에서 하나의 n이나 CI를 두 지표가 공유하는 것처럼 배치하지 않는다.
- 데스크톱은 표를 유지할 수 있다. 넓은 원본 표는 ‘계산 상세’ 안에서만 가로 스크롤하고, 스크롤 안내와 모델명 고정 열을 제공한다.
- 기본 본문 15~16px, 근거 13~14px를 시작점으로 검토한다. 터치 영역은 약 44px 이상, 키보드 focus와 details/summary의 펼침 표시를 유지한다. 도구 설명은 hover 외에 탭으로도 연다.

왜: 좌우 스크롤 없이 모델명과 판정·근거를 한 번에 읽게 한다. 글자 크기·간격 수치는 디자인 제안이며 실제 기기 검증 전이다.

| 뜻 | 권장 표현 | 색 사용 |

### P1-3. 기준일과 실패 상태를 각 구역에 붙이기

cross_sim의 기존 asof, recent_ic의 recent_span, alpha_beta의 asof를 해당 지표 옆에 표시한다. 데이터 생성일은 필요하면 별도로 보여 준다. leaderboard에는 확인한 범위에서 자체 asof가 없으므로 다른 파일 날짜를 대신 넣지 않는다. 보조 패널의 빈 catch는 사용자에게 ‘불러오지 못함’ 상태로 드러내고, 실패를 ‘모델 없음’과 구분한다.

왜: 서로 다른 기준일의 수치를 같은 날 성적으로 읽지 않게 하고, 빈 화면이 결과 없음인지 오류인지 알 수 있다.

### 데이터 제약: ‘최근 성적을 n·CI와 함께’는 지금 JSON만으로 완성할 수 없음

| 지표 | 현재 필드 | 지금 가능한 표시 |
|---|---|---|
| 누적 h20 IC | leaderboard의 h20.ic/n/ci | 세 값을 같은 묶음으로 표시 가능. 최근 수익으로 이름 변경 금지. |
| 누적 20거래일 초과수익 | exc20.mean/n/ci | 세 값을 표시 가능. 비교 대상은 같은 후보군 중간값이며, trailing의 시장평균과 다름. |
| 최근 1·5·20거래일 성적 | cross_sim.trailing의 r1/r5/r20, n, since | CI 없음. n은 등록 후 전체 이력 길이이며 각 기간 n이라고 가져다 쓰면 안 됨. |
| 최근 IC | recent_ic의 ic_recent/n_recent, ic_all/n_all | n은 있지만 CI 없음. 기존 leaderboard CI를 가져다 붙이면 다른 표본의 CI를 오용함. |
| 알파/베타, 고정 창 수익 | alpha_beta 및 cross_sim.panels의 n 등 | CI 없음. t 값을 CI로 바꿔 부르면 안 됨. |

**이번 제약을 엄격히 지키는 기본안**: n·CI가 없는 수익·IC 값은 개선 화면에서 숫자로 노출하지 않고 ‘이 기간의 표본·신뢰구간 정보 미제공’으로 표시한다. 누적 IC·exc20은 n·CI와 함께 제공하되 ‘최근 성적’의 답을 대체했다고 주장하지 않는다. 상세 펼침이나 툴팁으로 옮기기만 해도 n·CI 문제는 해결되지 않는다.

원한다면 ‘관측 경로의 실제 수익 기록은 CI 미제공이라고 적고 수치 자체는 허용’하는 정책을 따로 정할 수 있다. 그러나 이는 **이번 요청의 항상 n·CI 동반 조건에 대한 별도 승인 필요**다. 새 CI 계산·임의 신뢰 점수·다른 지표의 CI 전용을 제안하거나 실행하지 않았다. 최근 수익을 표본 추정치로 추론할지 단순 관측 기록으로 보여 줄지부터 결정해야 하므로, 이 보고서에서 임의 부트스트랩 계산식을 확정하지 않는다.

## 5. 다음 판정: 현재 페이지가 말할 수 있는 범위

- **현재 JSON만 사용**: qs_a·mom_b는 oos_days=36이다. 기존 화면의 40−36은 ‘최소 관측기간까지 4거래일’로 풀어 쓸 수 있다. 새 지표가 아니라 기존 카운터 설명이며, 미래 달력 날짜를 계산하지 않는다. 기간 충족 이후 결과는 확정 문서가 있어야 표시한다.
- **문서에는 있지만 현재 JSON의 일정 필드에는 없음**: v30 W2b는 원장·사전등록상 약 10/07 재판정이다. 사전등록 §2에 따라 기존 챔피언 유지와 2차 라벨 병기, 조건 충족 시 표시 기준 재검토 안건 또는 기각 절차로 갈릴 수 있다. ‘노이즈면 자동 은퇴’라고 줄이면 안 된다.
- sv_a 재판정은 해당 VERDICT의 ‘상승장 앵커 15개 또는 OOS 80 중 이른 때’다. 현재 D-40 화면으로는 이를 표현하지 못한다. le_a는 판정 완료 노이즈지만 문서에 다른 국면 표본 이후 재판정 여지도 적혀 있다.
- **제안**: 첫 단계에는 ‘재판정 일정은 현재 데이터에 미제공’과 검증된 근거 문서 링크를 제공한다. 이후 일정·조건·가능한 조치를 registry 등 표시용 데이터로 옮기는 작업은 별도 승인·구현 범위다. 이 검토에서 문서의 숫자를 새 JSON 값처럼 상수로 넣거나 미래 시점을 계산하지 않는다.

## 질문·확인하지 못한 것

1. REQUEST 말미의 유의 정의 ‘CI가 0을 넘지 않고’는 PROJECT_KNOWLEDGE §11의 ‘CI가 전부 0 초과’와 상충한다. 본 제안은 정본 §11을 따랐다. 요청 문구 정정이 필요하다.
2. REQUEST의 ‘노이즈는 판정 완료이며 새 model_id로만 재도전’은 판정 전 자동 노이즈·동일 모델의 추가 표본 재판정·은퇴 후 부활을 구분해야 한다. 현재 페이지와 문서에 서로 다른 사례가 있다. 사용자 UI에서는 상태와 판정 라벨을 분리하고, 모든 노이즈를 은퇴나 영구 종료라고 바꾸지 않는 안을 제안했다.
3. 최근 성적의 CI가 없는 상태에서 숫자 표시를 허용할지, n·CI가 공급될 때까지 숨길지 정책 결정이 필요하다. 이번 보고서의 기본안은 숨김이다. CI를 새로 만들려면 표본·대상 추정량·보유 중첩 처리부터 별도 승인 범위로 정해야 한다.
4. 공개 배포본·실제 390px 렌더·터치·스크린리더·색 대비·5초 이해도는 미측정이다. 수정본을 만들면 첫 화면에서 사용자가 ‘내 운용 기준, 확정 판정, 다음 검토’를 읽어 답할 수 있는지 직접 확인해야 한다.
5. 현재 각 JSON의 기준일·생성일이 다르고 leaderboard 자체 기준일은 확인되지 않았다. 최신 판정과 수치의 시점을 어떤 필드로 보장할지는 별도 구현 때 정해야 한다. 이번에는 DB나 계산 결과를 갱신하지 않았다.

## 반영 순서와 완료 확인

첫 반영 묶음은 **역할 표시·money 필터·잘못된 승률/확신 문구·트랙별 분리**다. 다음은 모바일 카드·n/CI 동반·기준일·오류 상태다. 일정 데이터 확장은 별도 작업이다. 외부 라이브러리·CDN 없이 기존 HTML/CSS/JavaScript와 details/summary로 구현 가능하다.

이번 작업은 독립 검토 문서 작성만이다. 점수·판정·게이트 변경, 새 모델 등록, DB 조회·쓰기, 수집기 실행, 커밋·푸시는 하지 않았다.
