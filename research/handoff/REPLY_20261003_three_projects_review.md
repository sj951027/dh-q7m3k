# 세 폴더 최근 변경 검토와 화면 개선 제안

검토일: 2026-10-03(KST) · 대상 변경: 10월 2~3일 · 작성: Codex 독립 검토

## 1. 먼저 읽을 결론

최근 변경은 데이터 누락을 줄이고, 참고 성적과 정식 판정을 나누고, PTW에서 출처 모델을 추적하는 방향으로 진행됐다. 이 방향은 유지할 만하다. 다만 **화면을 더 꾸미기 전에 성공·실패 표시, 대형 시세 소비 경로, 통계 표현의 정확성을 먼저 보완할 필요가 있다.**

화면은 필요한 정보가 많지만, 지금은 설명·비교표·과거 연구가 한 화면에 누적돼 있다. 사용자가 원하는 **“지금 무엇을 확인해야 하나 → 어떤 목록을 볼까 → 근거는 무엇인가”** 순서로 재배치하는 편이 낫다. 특히 ‘요즘 1등’을 강조하는 큰 문장보다 **기준일·표본·시험 당시 결론·다음 확인 조건**을 먼저 보여 주는 것을 제안한다.

## 4. 정확성과 운영에서 먼저 보완할 항목

### P1-1. PTW ‘저녁 완료’ 표식의 의미를 좁히거나 결과를 실제로 집계해야 한다

**직접 확인:** `app/main.py:710` 부근은 `send_evening_summary(db)`가 돌아오면 `evening_ok_at`을 기록한다. `app/compute.py:714`의 요약 함수는 사용자별 예외를 잡고 계속 진행한다. `_send_evening_one`은 `send(...)`의 반환값도 확인하지 않는다. 전송 함수가 실패를 False로 반환하거나 사용자별 예외가 삼켜져도 바깥 작업은 끝난다.

**합성 재현:** 실제 요약 함수와 cron 내부 `_do`를 추출하고 요약 발송을 실패하게 했을 때도 완료 표식 기록이 실행됐다. 자산·운영 DB·텔레그램에는 접근하지 않았다.

**영향:** `/api/cron/evening_status`의 200을 ‘계산 및 모든 알림 성공’으로 읽을 수 없다. v5.31 문서의 “전송이 예외로 죽은 날도 503”과 실제 코드가 맞지 않는 경로다. 스냅샷·신호이력 저장도 비치명 예외 처리이므로 완료 표식 하나로 그 성공까지 보장하지 못한다.

**제안:** 핵심 계산은 계속 살리되, 계산 완료 / 기록 완료 / 요약 전송 성공·실패·대상 없음 상태를 별도로 집계한다. 상태 조회는 필요한 항목의 실패를 알려 주고, 사용자 화면에는 실패한 부분만 짧게 표시한다. 실패 후 재시도에서 같은 요약이 중복 발송되는지도 함께 확인한다.

**수정 완료 조건:** 전송 False·사용자별 예외·저장 실패·대상 없음·전원 성공을 각각 주입해 결과가 구분됨. 신호 판정값과 알림 diff 기준은 그대로.

### P1-2. 대형 판정의 부족 표본 처리가 보수적으로 닫혀 있지 않다

**직접 확인:** `large_verdict.py:133`은 비겹침 통계의 `ic`가 None이 아닐 때만 ‘유의’를 낮춘다. 따라서 비겹침 자료가 없어도 이 보완 검사는 작동하지 않는다. 표본 1개에서 나온 `[같은 값, 같은 값]` 구간이 양수여도 그대로 통과할 수 있다. 또 최소 8개 검사는 `st['n']`이 아니라 날짜상 보유기간이 끝난 `nclosed`를 본다. 시세 결손으로 실제 계산 가능 표본이 줄어드는 경우 두 수가 다를 수 있다.

**합성 재현:** 기존 라벨을 ‘유의’로 놓고 실제 조건문에 비겹침 n=0 및 n=1을 넣었을 때 둘 다 ‘유의’가 유지됐다. **현재 실제 h60·h120 상태 파일은 모두 대기다. 지금 잘못 채택됐다는 뜻은 아니다.**

**제안:** 부족 표본에서는 ‘검증 자료 부족’으로 남겨 두는 규칙을 명시한다. 날짜상 완료 수와 IC 계산 가능 수를 따로 표시하고, 비겹침 0·1개 상태를 확신의 근거로 쓰지 않는다. 충분한 표본 기준, 겹침을 처리하는 방법, h60/h120 결론의 관계는 사용자 결정과 사전등록 보완이 먼저다. 이 문서에서 새 숫자를 정하지 않는다.

**정본성 문제:** ISO 주 첫 앵커·최소 8개·분모 1·비겹침 보완 규칙은 코드와 작업기록에 있지만 원래 `PREREGISTER_ls_t1.md`에 이 상세 규칙은 없다. 작업기록도 일부가 구현자의 결정임을 적고 있다. `leaderboard.verdict` 재사용을 ‘정본 §9 판정’이라고 확정하기 전에 합의된 절차와 구분해야 한다. 특히 해당 함수는 95% 구간과 단순 보조 조건을 쓰므로 정식 판정문에서 수행하는 검증 전체를 자동 대체한다고 보지 않아야 한다.

**수정 완료 조건:** 비겹침 0/1개, 날짜상 8개지만 유효 표본 미달, 한 시장 결손, h60/h120 상반 결과를 합성 검증. h20 일치 검사는 공유 함수를 공유 함수와 대조한 것이므로, 별도로 작은 손계산 예제도 필요.

### P1-3. 보충 시세의 소비 경로가 성적표까지 이어지지 않았다

**직접 확인:** `leaderboard.py`의 ls_t1 부분과 `large_verdict.py`는 `daily_ohlcv_extra`를 합친다. 반면 `build_scoreboard.py:224`는 본 표만 읽은 `close`를 모든 모델에 전달한다.

DB 대조 결과:

- 등록 이후 대형 점수가 있는 542종목 중 본 표에 없는 종목 48개, 본 표+보충 표에서는 없는 종목 0개.
- 최신 20261002 대형 점수의 시장별 상위 10에서, 코스닥은 **6/10**종목이 본 표에 없다. 코스피는 0/10.
- 성적표는 시세 있는 종목을 남긴 뒤 최소 5종목 조건을 확인한다. 이처럼 4종목만 남는 시장은 계산에서 빠질 수 있다.

**영향:** 동일한 ‘대형밸류 ls_t1’이라도 검증 자료와 40일 성적표·PTW의 계산 대상이 다르다. 현재 대형의 40일 완료분은 아직 없어 영향은 우선 오늘 가격 기준 참고값과 앞으로 생길 완료분에 해당한다. 이 검토에서 보충 적용 후 수익 차이 전체는 재계산하지 않았다.

### P1-4. 보충 수집의 실패 수가 배치 실패 표시로 전달되지 않는다

**직접 확인:** `extra_ohlcv.py:165`에서 `collect()`의 반환값 `n_skip`을 받지만 다음 줄은 항상 0을 반환한다. 배치 파일은 0이 아닌 종료코드만 `FAILED`에 더한다.

**수정 완료 조건:** 전부 성공 / 일부 수집 실패 / 전부 실패 / 자료 없음 / DB 없음 사례별 종료·상태가 기대대로 나오고 알림에도 이유가 전달됨.

### P1-5. 묶음의 사후 선택과 겹침 구간을 화면에서 더 분명히 해야 한다

**수정 완료 조건:** 과거 재구성과 향후 관찰을 구분하며, 멤버의 판정 전 날짜가 앞으로 검증한 표본처럼 집계되지 않음. 단정 문구 제거. 기존 개별 모델 값 불변.

## 5. 숫자와 말의 정확성

### 5-1. PTW ‘진행 중 포함’ 설명은 실제 계산과 다르다

`build_scoreboard.py:58,100`의 `now`는 40일 미만 건만의 평가가 아니라 **모든 매수 기준일을 오늘까지 계속 보유했다는 값**이다. v30은 완료 38일, `now`는 전체 75일이다. PTW는 아래 설명에서 “아직 40일이 안 된 매수분을 오늘 가격으로 계산한 값”이라고 적는다(`app/static/index.html:949` 부근).

제안: 지금 계산을 유지한다면 ‘모두 오늘까지 보유 가정’으로 바꾸고 상세로 내린다. ‘40일 완료분 + 미완료분 현재 평가’를 원한다면 별도 계산이므로 기존 값과 섞지 않는다. 사용자가 두 숫자의 차이를 최근 흐름으로 잘못 읽지 않게 해야 한다.

### 5-2. 쉬운 말이 통계의 뜻을 바꾸지 않도록 한다

| 현재 표현 | 문제 | 제안 |

표시 규칙 변경 제안이며 판정 라벨·점수·사전등록을 바꾸자는 뜻이 아니다. `DISPLAY_TERMS.md`도 같은 결정에 맞춰 갱신해야 화면마다 다시 갈라지지 않는다.

### 5-3. 날짜와 상태는 자유 문장에서 추출하지 않는다

- `build_scoreboard.py:112`는 판정 문구의 M/D 앞에 **현재 데이터의 연도**를 붙인다. 2027년 자료가 들어오면 2026년 판정이 2027년으로 바뀌는 구조다. 직접 확인한 잠재 오류이며 실제 2027년 실행 재현은 하지 않았다.
- `verdict_window`는 등록일부터 40거래일을 계산해 표시한다. 모델별 실제 판정 기록·재판정 창을 모두 정확히 표현하는 필드가 아니다.
- le 화면의 제목·상태는 ‘검증 중’, 본문은 ‘판정 완료·판정 종료’다. ‘판정 완료 / 적재·관찰 계속’의 두 상태로 분리할 필요가 있다.
- 대형 화면 생성기에는 아직 `h=60/120d(9월~)`가 남아 있다. 새 상태 문서는 h60 첫 창까지 23거래일, 주간 8개까지 추가 약 7주를 적는다.
- `first_done_eta`의 `남은 거래일 × 1.45`는 휴장일 달력이 아니다. ‘~10/09’처럼 현재 skip_dates에 있는 날이나 ‘~10/31’처럼 주말이 화면에 나올 수 있다. ‘앞으로 약 N거래일’과 실제 판정 조건을 나눠 표시하는 편이 정확하다.

제안 필드: `verdict_date`, `window_start`, `window_end`, `label`, `recording_status`, `next_review_condition`. 정본 기록에서 채우고, 구형 JSON에서는 ‘날짜 확인 필요’로 표시한다. 날짜를 추정해 확정값처럼 만들지 않는다.

### 5-4. ‘가장 앞섰다’는 문장에 비교 기간이 빠져 있다

현재 완결 표본은 v30 38일(6/5~8/3), le_a 13일(7/15~8/3), qs_a 8일(7/23~8/3)로 서로 다르다. 각각의 등록 후 참고 평균을 보여 주는 것은 가능하지만, 이를 공정한 동일 기간 승자 순위처럼 강조하면 안 된다.

제안: 기본 표에 기간·완료 기준일 수를 노출하고, 표 위에 ‘등록 이후 각각의 기록: 비교 기간 다름’을 둔다. 비교용으로는 **같은 시장·같은 기간에 겹치는 날짜만 보기**를 추가할 수 있다. 이것 역시 화면 비교용이고 정식 판정은 그대로 둔다. 트랙 A와 대형·주도주의 잣대는 별도 유지한다.

### 6-3. PTW: 실제 손익과 모델의 가상 기록을 시각적으로 구분한다

**직접 확인:** 로그인된 실제 통계 탭의 ‘모델 성적’이 정상 로딩된다. 기본 4개 모델, 전체 13개 펼침이 있고 기준일을 표시한다. 다만 스크리너는 쉬운 판정 용어를 쓰는데 PTW는 `노이즈`, `유의(8/09 정본)` 등을 그대로 표시한다. `_sb_trim()`은 새 시장별·형세·판정일 구조를 전달하지 않는다.

**제안:**

- 통계의 두 영역을 **내 매매 기록 / 모델 가상 기록**으로 구분한다. 출처별 개인 손익과 스크리너 모델 성과를 같은 지표처럼 비교하지 않는다.
- 모델 카드의 기본값은 이름·자료 기준일·완료 기록·표본·당시 결론만. ‘모두 오늘까지 보유 가정’은 상세로 내린다.
- 각 모델에 ‘목록 보기’, 전체 성적표에 ‘스크리너 성적표 열기’를 제공한다.
- 큰 트랙 구분을 별도 카드/구획으로 한다. 대형을 같은 숫자 열에 별표 하나로 놓는 것보다 비교 대상이 다르다는 사실을 알아보기 쉽다.
- 출처 모델은 ‘어디서 골랐나’, 전략 태그는 ‘어떤 관리 규칙인가’로 설명한다. `#저점탈출`의 40일 리마인더가 검증된 보유 권고가 아님을 현재 설계대로 유지한다.
- 실패 후 마지막 성공 데이터를 보여 준다면 기준일 옆에 ‘이전 자료 표시 중’을 붙인다. 현재 API는 마지막 성공값을 유지하지만 그 사실을 별도 상태로 내려주지 않는다.

운영 대시보드 전체를 개인 금액이 보이는 스크린샷으로 보관하지 않았다. PTW의 모바일 전체 흐름·입력·오류 상태는 이번에 실측하지 않았다.

### 6-4. 검증 자료·알림

검증 자료에는 20종목 따라사기·20일 순위 검증·40일 성적표가 서로 다른 잣대라는 안내를 각 표 바로 위에 둔다. 현재 ‘② 확신’ 설명은 시장 대비 수익의 구간과 판정을 연결해 읽히는데, 순위 IC 판정과 돈 기준은 다르므로 분리해야 한다. `IC 0.01 ≈ 시장초과 +0.3%p`도 고정 환산식처럼 두기보다 특정 연구 구간의 관측으로 접어 두는 편이 낫다.

일간 알림은 ‘자료 상태 / 모델 참고 기록 / 다음 확인 / 링크’의 네 블록을 유지한다. 종목·모델별 장문 풀이보다 실패한 단계와 자료 기준일을 먼저 적는다. 주간 알림은 일간과 기준이 다르면 ‘이번 주 실제 가상 경로 수익’처럼 계산 대상을 명시한다. 알림을 짧게 하려고 표본·기준일·차이의 단위를 빼지는 않는다.

### 6-5. 상호작용·색·접근성

- 성적표 상세는 `tr.main` 클릭으로 열리며 행 안에 별도 상세 버튼이 없다. ‘상세’ 버튼과 펼침 상태(`aria-expanded`)를 제공해 키보드·터치 동작을 분명히 한다. 목록 링크와 상세 펼침 영역을 분리한다.
- 수익의 양·음과 판정의 확정 수준을 같은 색으로 표현하지 않는다. 부호·단위·텍스트를 항상 병기한다.
- 숫자는 자릿수와 소수점 자리를 통일하고, ‘자료 없음 / 아직 기간 미완료 / 적용 대상 아님’을 모두 `—`로 표현하지 않는다.
- 주의 문구 전체를 작은 회색 글씨로 밀어내지 않는다. 의사결정에 중요한 ‘기간 다름’, ‘표본 부족’, ‘사후 선택’은 해당 값 옆에 둔다.
- 화면 전체를 새 프레임워크로 옮길 필요는 없다. 먼저 기존 HTML·React에서 정보 순서와 공통 표현을 고치는 편이 검토 범위가 작다.
