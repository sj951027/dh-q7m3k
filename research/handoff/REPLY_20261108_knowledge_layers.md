# REPLY — 지식 세 층 구조 검토 — 2026-11-08

**세 층 구분은 유지하는 편이 좋다. 다만 지금 부족한 것은 요약의 양보다 ‘적용 대상·현재 상태·재검 조건·정본 우선순위’다. 이미 구현된 일을 미구현으로 읽거나, 새 후보에게만 적용할 조건을 기존 모델에 붙일 수 있는 어긋남이 있다.**

검토 범위: 최신 worklog 1건 → 세 장 → 원장을 읽고, 관련 규약·지도·구현·테스트 소스를 대조했다. 아래 **실측**은 파일에서 직접 확인한 내용이다. ‘다음 세션이 할 실수’는 그 어긋남에서 예상한 **위험 시나리오**이며, 기억 없는 별도 참가자로 실험한 결과는 아니다. 코드·테스트·배치 실행과 DB 접근은 하지 않았다. 이 답변 파일 외에는 만들거나 수정하지 않았다. 줄 번호는 검토 시점 작업본 기준이다.

## 1. 새 세션이 틀릴 수 있는 것 3가지

### 1) lv_e에 돈 조건을 새 탈락 조건으로 붙이거나 다시 승인받으려 함

**실측:** `KNOWLEDGE.md:27`은 lv_e 승격을 ‘2차 창 + 돈 관측표 뒤’로, 45행은 승격을 ‘두 창 + 돈 관측표 하단 > 0’으로 요약한다. `DECISIONS.md:39`도 적용 대상 예외 없이 같은 방향으로 적는다. 그러나 **`VERDICT_RULES.md:81`과 `research/OBSERVATION_CONTRACT_20261104.md:15`는 돈 조건을 2026-11-07 이후 신규 후보부터 적용하고 기존 모델은 참고로 병기**한다고 명시한다. `MODELS_LEDGER.md:13`도 신규 후보라는 범위를 보존하며, 27행의 lv_e 등록일은 2026-09-01이다.

**예상 오류:** 12월에 lv_e의 돈 관측표 하단이 양수가 아니거나 코호트가 부족하다는 이유만으로 기존 모델의 표시 기준 교체를 막거나, 이미 정한 적용 범위를 다시 사용자에게 묻는다. 이는 규칙을 더 엄격하게 지키는 것이 아니라 요약 과정에서 적용 대상을 바꾼 것이다.

**제안 문구:**

> lv_e 표시 기준 교체는 관측 계약의 두 창 조건으로 판단한다. 돈 관측표는 기존 모델에 참고 병기한다. 돈 조건을 필수로 적용하는 대상은 2026-11-07 이후 신규 후보이며, 신규 후보에는 코호트 4개 이상·구간 하단 > 0이 필요하다. 11/11 승격 재질문은 하지 않는다.

**기대 이득:** 기존 승인 범위와 새 후보 규칙을 혼동하지 않는다. **비용:** 정리 담당자가 해당 요약 행들에 적용 대상과 계약 링크를 한 번 보완하고, 계약 변경 때 그 행들만 대조한다. 규약 자체의 변경 제안은 아니다.

### 2) 업종 스냅샷 구현을 다시 다음 일로 고름

## 2. 형식 — 추가할 것은 적용 범위와 상태, 재검 조건

### 먼저 지식 층의 권한을 좁히기

**실측:** `CLAUDE.md:8`과 `KNOWLEDGE.md:3`의 ‘여기 없는 결론은 아직 결론이 아니다’는 요약 누락을 결론 부재로 취급한다. 같은 문서의 원장·사전등록 우선 원칙과도 맞지 않는다. `KNOWLEDGE.md:4`의 ‘실측 = 문서에 숫자 있음’ 역시 숫자의 존재와 독립 확인을 구별하지 못한다.

**제안 문구:**

> 이 문서는 정본을 찾는 요약이다. 미등재는 미확인 상태이며 결론 부재를 뜻하지 않는다. 충돌 시 해당 주제 정본과 승인된 개정·적용 범위를 확인한다. 정본의 숫자를 옮긴 것, 독립 재현된 것, 해석을 구별한다.

**기대 이득:** 요약을 압축하다가 승인·결론이 사라지거나 근거 수준이 올라가는 일을 막는다. **비용:** 정리 담당자가 새 행에 근거 상태를 짧게 표시하고, 충돌 때만 원문을 연다. 이미 정한 판정·배치·0-diff 규칙의 우선순위는 그대로다.

### 권장 형식 — 새 장부 없이 기존 세 장 안에서

| 문서 | 제안하는 보완 | 기대 이득 | 비용: 누가 언제 무엇을 하나 |
|---|---|---|---|
| KNOWLEDGE | `ID·자리·축 / 적용 범위 / 결론·근거 상태 / n·효과[CI]·기간 / 닫힌 이유 / 재검 조건 / 정확한 정본 링크`로 읽히게 한다. 적용 범위에는 대리/실제 모델·지평·비교 대상·비용을 포함하되, 공통 정의 링크로 줄여도 된다. | 서로 다른 표본·모델의 결론과 잠정 해석을 한 사실로 합치지 않는다. | 연구 담당자가 새 결론마다 범위와 근거 상태를 채운다. 기존 행은 수정할 때 나눠 옮긴다. |

현재 ‘한 행=한 결론/결정’과 달리 `KNOWLEDGE.md:14`는 네 축, `DECISIONS.md:18`은 실적 배지와 휴지통 정책을 묶는다. **재검 시점·승인 범위가 다르면 행도 나눈다.** 날짜만으로는 같은 날의 여러 결정을 식별할 수 없다. 이 분리의 이득은 한 결정을 대체할 때 무관한 결정까지 바뀌지 않는 것이며, 비용은 정리 담당자의 최초 행 분리다.

### 재검 조건의 자리와 의미

**제안:** KNOWLEDGE의 ‘닫힌 이유/뒤집힐 곳’을 **닫힌 이유**와 **재검 조건**으로 구분한다. 후자는 `발동 조건 → 다시 할 확인 → 누가 결정하는가 → 정본` 순으로 쓴다. DECISIONS에는 해당 지식 ID와 승인 조건만 연결한다. 재검 조건 충족은 **재검토 시작**이지 등록·채택·규칙 변경의 자동 승인이 아니다.

예시(현재 기록을 구체적으로 연결하는 방식):

- `바깥 세 축: 닫음·상대방 재현 대기 → Claude 재현이 어긋나면 원인 대조 → 등록/규칙 변경은 별도 결정` (`KNOWLEDGE.md:20`).
- `연기금×A: A 사건 30개에 재검 → 표본·방향 확인 → 그전에는 후보 유지` (62행; 정본의 사건 정의를 함께 링크).
- `수급: 12월 초에 10월 완결 자료를 확인 → 기존 §5-1 조건으로 대조 → 등록은 그 뒤 결정` (37행). 날짜가 됐다는 이유만으로 조건을 통과한 것으로 쓰지 않는다.
- `업종 스냅샷: 구현 완료 → 같은 기능 재구현은 없음; 관측 이력의 충분성은 별도 자료 조건`.

**기대 이득:** ‘닫음=영구 금지’와 ‘다음 달=재승인’의 양쪽 오해를 막는다. **비용:** 결론 작성자가 재검 조건을 1회 정의한다. 조건이 없으면 `미정·임의 재개 안 함`으로 명시하고, 매번 사용자에게 묻지 않는다. 연구 문턱을 새로 정하거나 낮추자는 제안은 아니다.

| **정본 경로·절:** 기존 `test_knowledge_sheets.py` 보완. 정본 칸은 저장소 상대 경로의 Markdown 링크로 통일하고, 없는 파일·명시된 제목 앵커·모호한 축약명을 검출 | 추가 50~80줄 | 예. 결정적인 형식 오류만 실패 | 검사에서 빠지는 축약 정본을 줄임 | 최초 링크 정리는 문서 담당자, 이후 작성자는 실제 경로 선택. 외부 웹은 테스트 중 접속하지 않음 |
| **ID·상태·대체 관계·재검 필드:** 중복 ID, 없는 대체 대상, 대체 순환, 무효 상태값, 필수 필드 누락 검사. `\|`가 들어간 표도 처리 | 추가 60~100줄 | 형식 합의·기존 행 전환 뒤 예 | 부분 대체와 오래된 상태를 추적할 수 있음 | 최초 형식 전환 후 작성자가 상태/ID를 채움. 의미의 타당성은 사람이 확인 |
| **모델 포함 범위:** 원장 현역 표에서 model_id를 읽고 지식의 모델 참조 전체와 비교. 은퇴는 별도 범주, 원장 별칭·중복 창은 정규화. ② 자리 완전 일치는 요구하지 않음 | 추가 40~70줄 | 예. 누락/모르는 ID만 실패 | 새 모델이 고정 검사 목록에서 빠지는 일을 막음 | 원장 담당자가 기존 모델 ID 형식을 유지. 추가 고정 모델 목록은 관리하지 않음 |
| **크기·정리 주기:** 상한은 현재 검사 유지. 마지막 정리 날짜와 마지막 검토 worklog 위치를 기록해 ‘30일 또는 새 기록 10건’ 점검 알림 | 추가 25~45줄 | 날짜 형식·크기만 예; 기간 도래는 경고 | 정리 시점을 사람이 세지 않아도 됨 | 정리 담당자가 두 기준을 완료 시 갱신. 한 파일에 여러 세션을 덧붙이는 현재 방식에서는 ‘10건≠10세션’이므로 실제 세션 구분 전에는 월 기준만 확실히 사용 |
| **결정 누락 후보:** 제안 위치 `research/check_knowledge_drift.py`. 정리 이후 worklog의 ‘사용자 결정’ 절과 DECISIONS의 출처 링크/ID를 비교 | 약 60~100줄 | 아니오. 정리 때 읽기 전용 경고 | 기록에만 남은 승인 후보를 모아 줌 | 문서 담당자가 경고만 확인. ‘결정 없음’, 같은 날 다른 결정, 인용된 옛 결정이 있어 날짜·단어만으로 실패 처리하거나 자동 승인하지 않음 |

전체 의미 모순을 문자열 검사로 해결하려고 하지 않는다. 특히 `CI가 0을 포함함 → 효과 없음`, `대리 결과 → 실제 v30 채택` 같은 해석은 원문 대조가 필요하다. **자동 검사는 누락·형식에 집중하고, 정기 검토는 바뀐 행과 그 정본을 대조하는 데 집중**하는 안이다. 이득은 검사 통과를 내용 검증으로 오인하지 않는 것이며, 비용은 정리 담당자의 변경 행 검토다.

## 4. 바깥 방법과 비교 — 두 가지만 차용

### ADR의 상태·대체 관계 → DECISIONS에 적합

**외부 확인:** Michael Nygard의 ADR 설명은 하나의 중요한 결정에 맥락·결정·상태·결과를 남기고, 번복된 결정도 지우지 않고 대체 기록을 연결한다. [원문: Documenting Architecture Decisions](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions).

**제안:** 이 원칙을 DECISIONS의 ID·적용 범위·대체 관계에만 사용한다. 모든 작은 문구 변경마다 별도 ADR 파일을 만들 필요는 없다. **기대 이득:** 다음 세션이 ‘왜 바뀌었고 무엇이 아직 유효한가’를 알 수 있다. **비용:** 결정 기록 담당자가 중요한 변경 때 이유와 구·신 ID를 연결한다. 새 승인 절차는 추가하지 않는다.

### 사전등록의 계획·결과·사후 변경 구별 → 연구 정본에 적합

**외부 확인:** Center for Open Science는 사전에 적은 계획과 결과를 보고 추가한 분석을 구분하고, 계획에서 달라진 부분을 투명하게 보고하도록 설명한다. [공식 안내: Preregistration](https://www.cos.io/initiatives/prereg).

**제안:** 기존 `PREREGISTER_*`와 연구 §0을 유지하면서 지식 행에는 `사전 계획/탐색·사후`, 계획 버전, 결과 및 재현 링크를 남긴다. **기대 이득:** 요약이 ‘사후 관측’을 ‘사전 검증 통과’로 바꾸지 않는다. **비용:** 연구 작성자가 시작 시 버전, 마감 시 계획 대비 변경 여부를 기록한다. 외부 서비스 가입·공개 업로드·새 저장소 도입은 필요하지 않다.

**이번 목적에 덜 맞는 것 — 제안:** 실험실 노트처럼 시간순 기록을 매번 처음부터 읽는 방식은 현재 worklog 문제를 반복한다. 일반 의사결정 로그를 하나 더 두는 것도 DECISIONS와 중복된다. 다만 원자료·실험 경과·실패 경위는 기존 기록 층에 계속 보존한다. **기대 이득:** 새 문서 체계를 늘리지 않는다. **비용:** 기존 기록 담당자의 작업은 유지하고, 요약과 출처 연결만 추가한다.

## 5. 읽기 순서에서 뺄 것 — 삭제가 아니라 필요할 때 읽기

**실측:** `CLAUDE.md:10`은 이미 PROJECT_KNOWLEDGE의 필요한 절만 읽으라고 한다. 12행의 지도 필수 범위는 §2·§3·§6으로, **§10 전체는 현재도 매 세션 필수가 아니다.** 따라서 ‘이 두 문서를 전부 읽던 의무를 없앤다’고 설명하면 현 규칙을 잘못 요약하게 된다.

| 문서·범위 | 제안 | 빼면 잃는 것·보완 | 기대 이득 | 비용 |
|---|---|---|---|---|
| 지도 §10 시간순 | 일반 시작 읽기에서 제외 유지. 지식 행의 출처가 가리킬 때만 해당 항목 열기 | 정정 이유·탐색 경로. 원문 링크를 남김 | 같은 이력을 여러 번 읽지 않음 | 정리 담당자가 정정 항목을 지식과 연결 |
| PROJECT_KNOWLEDGE §8 향후 작업·§10 변경 이력·과거 결과 서술 | 일반 세션에서 생략. **§2~4 구조·점수, §6 규칙, §11 및 해당 사전등록은 관련 작업 때 유지** | 구현 의도·옛 판정 문맥. 코드 검토/판정 때 필요한 절을 읽음 | 150KB 문서의 반복 읽기를 줄임 | 작업자가 대상 모듈·판정의 절만 선택 |
| OPS_GUIDE | 일반 연구 시작에서는 생략, PTW 안내·운용 권고를 다룰 때 읽기 | ‘권고와 실제 제한의 구별’, 사용자 자유·운용 방식의 맥락 | 규약 아닌 권고를 현재 판정 조건으로 혼동하지 않음 | 해당 작업 담당자만 §0~4 확인 |
| 최신 patch_note 3~4건 | 일괄 읽기 대신 최신 worklog/요청서가 가리키는 변경과 작업 대상 패치만 | 다른 모듈의 최근 변화. 운영 장애·모듈 연결 검토 시 범위를 넓힘 | 무관한 이력 읽기를 줄임 | 작업자가 변경 대상과 연결 지점을 확인 |

반대로 **정본 확인은 뺄 수 없다.** 판정 작업은 해당 사전등록·판정문·VERDICT_RULES, 자동화 작업은 해당 단계 장부·설계, 새 연구는 지도의 관련 후보·금지 범위를 계속 확인해야 한다. 세 장은 입구이지 이들을 대체하는 규약이 아니다.

**권장 시작 흐름 — 제안:** 최신 worklog 1건 → 세 장 → 원장 → 현재 요청에 해당하는 정본/지도 행만 읽기. 세 장 사이 상태가 다르면 사용자에게 재승인을 묻기 전에 코드·승인 출처를 대조한다. 확인할 수 없는 권한·의도 차이만 질문으로 남긴다. **기대 이득:** 읽는 양을 줄이면서 기존 결정을 지킨다. **비용:** 담당자가 대상 정본을 선택하고 충돌한 행을 수정 후보로 기록한다.

우선순위는 **① lv_e 적용 범위·스냅샷 상태·국면 정의 정정 → ② 정확한 정본 링크와 대체 관계 → ③ 기존 자동 검사 보완 → ④ 일반 시작 읽기 축소**가 적당하다. 이번 답변은 제안만이며 규칙·형식·검사·문서 읽기 순서를 실제로 바꾸지는 않았다.
