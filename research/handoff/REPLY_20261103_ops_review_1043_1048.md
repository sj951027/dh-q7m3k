## 3. settle_days 회계

### 문제 없음 — 코드 확인 및 합성 실측

순서는 만기 매도 → 오늘 결제액 현금화 → 현금 한도 내 진입 → 평가이다. `NAV = settled cash + holdings value + pending proceeds`; 신규 예산은 `min(cash, 전날NAV/slots × ratio)`여서 pending을 직접 쓰지 않는다.

합성: 시작자산1, 슬롯1, 비용0, K1을 D1에100으로 사서 D3에120으로 청산; K2는 D3 진입 예정.

| 결제 지연 | D3 NAV | D3 현금 | D3 보유 평가 | 끝(D7) NAV / 현금 |
|---|---:|---:|---:|---|
| 0 | 1.2 | 0 | 1.2(K2 매수) | 1.2 / 1.2 |
| 2 | 1.2 | 0 | 0(K2 미매수) | 1.2 / 1.2 |
| 20 | 1.2 | 0 | 0 | 1.2 / 0 |

지연20은 관측기간보다 길어 끝까지 pending이지만 NAV에서 사라지지 않는다. 미매수 종목을 결제일에 자동 재시도하지 않는 것도 현재 규칙이다. 마지막 날 pending을 강제 현금화하지 않는 처리는 맞다. 다만 반환 표에 pending 열/결제 예정표가 없어 `NAV−cash−invested`로만 잔액을 알 수 있다. 돈 탭에는 별도 노출이 필요하다.

`settle_days=2`는 **매도대금을 결제일까지 재사용하지 않는 모의 가정**이다. 실제 증권사의 주문가능액 규칙을 검증한 결과로 해석하지 않는다.

### “0-diff”의 정확한 범위

- 기존 테스트 두 파일은 모두 통과했다. I절의 기본값 대 명시0은 같은 코드의 같은 경로를 검사한다.
- 추가로 `git show 3ee6cf2^:paper_engine.py`를 메모리로 읽어 새 함수와 비교했다. seed731, 90일·4종목, hold10, 슬롯1/7/40 × 비용0/.005/.01의 9조건. **NAV 최대 차이는 9.992007221626409e-16**.
- 슬롯40 세 조건의 포지션 수는 같았고 NAV 차이는 각각 `2.22e-16 / 3.33e-16 / 8.88e-16`. 따라서 이 예에서는 수치 허용오차 내 동등이며 비트 단위 동일은 아니다.
- 슬롯1·비용.01에서는 구/신 장부 수121/125, 일별 포지션 수 최대 차8. 극소 양수 현금으로 예산이 0보다 커져 생기는 포지션이다(신 장부 중 투자액 `0<invested<1e-14` 36개). NAV 영향은 `4.44e-16`. 금액 손실이 큰 오류로 분류하지 않았다.

## 4. 부모/자식·JSON·비밀 출력·배치

**부모만 모의 실행**했다. subprocess.run·DB 연결·JSON 작성·임시파일·replace를 전부 대체하여 자식/네트워크/실 DB 쓰기/실 파일 쓰기 없음.

| 자식 반환 조건 | 부모가 만든 refresh_status | 비고 |
|---|---|---|
| exit0, STATUS 없음 | failed / `worker exit 0, no status` | 로그인 import 실패 등이 바깥 예외처리로 끝나면 이 경우 가능 |
| `STATUS bad` | failed / JSONDecodeError | 예외 본문 대신 형 이름 |
| 한 시장 성공·다른 시장 실패 | **ok**, markets 안에는 실패 정보 | F1 |
| TimeoutExpired(300) | timeout / `>300s` | 실제 300초 대기는 하지 않음 |

- 인코딩은 subprocess에서 UTF-8·errors=replace. STATUS JSON 문법이 깨지면 failed로 간다. 코드상 마지막 STATUS 줄을 선택한다. 자식 returncode와 유효 STATUS의 모순을 따로 검증하지는 않는다.
- 위 상태는 **후속 DB 읽기와 JSON 저장이 성공할 때** 새 JSON에 남는다. DB가 아예 없으면 main이 일찍 return하여 옛 JSON이 남고, DB/JSON 생성 중 예외도 새 실패 상태를 게시하지 못한다(F3).
- 수급 JSON의 임시 파일→`os.replace`는 잘린 최종 JSON을 막는 방향으로 맞다. replace 이전 실패라면 기존 최종본이 유지된다. 실패 임시파일 정리 보장은 없다.
- **비밀의 로그 혼입: 검토한 배치→부모→자식의 정상/예외 경로에서는 불가능하도록 차단되어 있다.** pykrx import·조회 stdout/stderr를 redirect하고 부모도 자식 원문을 출력하지 않는다. STATUS에는 숫자·고정 설명·예외 형 이름만 싣는다. `_load_dotenv()` 소스도 값을 출력하지 않는다. 실제 로그인·자격증명을 사용한 시험은 하지 않았고, 라이브러리가 별도 로그 파일·상속한 다른 핸들로 쓰는 경로까지 검증했다는 뜻은 아니다. `.env` 파일은 열지 않았다.
- `run_all_and_diversify.bat`: 비ASCII 바이트0, CRLF211, 단독LF0. `run_auto_logged.bat`도 비ASCII0, CRLF37, 단독LF0. 수급66행, 모의계좌128행 뒤 다음 명령을 이어 실행하며 두 단계는 비치명 종료0 정책. 모의계좌 다음129행에 data_health가 오지만 F1/F3의 공백은 남는다.
